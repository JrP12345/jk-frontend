# Offline preparation and common calculation increment

> Historical increment report. The later [connected final-offline implementation](pharmacy-offline-final-billing-2026-11-15.md) supersedes the disabled-checkout and remaining-work status below. Enrollment/preparation alone still grants no billing authority; verified activation is separate.

Continues the [implementation plan](pharmacy-offline-final-billing-2026-11-15.md) and [ownership/performance increment](pharmacy-ownership-and-performance-2026-11-15.md). **Actual counter Save still requires internet. Offline checkout is not enabled by this work.**

## Implemented

- The existing server paise calculator now has one dependency-free source at backend `utilities/pharmacyCalculation.ts`. The existing service adapts its validation errors to the established `CommandError(409)` contract. Existing calculations, source-credit allocation and return math are preserved. Browser code is generated from that source; frontend builds need no sibling repository or runtime calculation request. The generator's `--check`, server source-digest test and browser artifact test detect drift.
- Signed ownership evidence captures the calculator policy and SHA-256 source digest. Local provisioning rejects a different digest, persists the prepared version in the encrypted ledger head and captures it in each immutable receipt. A changed engine cannot silently start new bills against old preparation. Exact recovery of an already committed bill remains available.
- The ledger recomputes prices from weighted captured lot allocations, declared line discounts, invoice discount, GST and explicit round-off before any invoice/stock/payment/number write. It compares every calculated line and total component, printed item values and document kind. MRP violations, unsafe multiplication, conflicting discounts, incorrect GST decomposition, incomplete calculations and anonymous high-value bills fail before commit. This is arithmetic validation, not product/operator authorization.
- Initial stock encryption runs in groups of 200 with interaction yields instead of starting up to 50,000 crypto operations together. Keys, stock, number state and usable ledger visibility still publish only in the final strict IndexedDB transaction; there is no financial memory-only fallback.
- Issuer profile edits and medicine tax/dispensing classification now obey held branch ownership. Valid edits roll back while held, and continue normally after audited unused-preparation release. Professional-review revocation is not frozen.
- An internal preparation service freezes reviewed ordinary stock, issuer identity, unit/tax revisions, eligible captured lot prices/MRP/expiry, branch/operator/device scope, the reserved numbering allocation and calculator digest. It validates owned captured lots and aggregate stock, excludes restricted/unreviewed products, and includes no patient, acquisition-cost or payment data. Initial preparation supports tracked inventory only, matching the current cash-ledger scope.
- Preparation is bounded to 10,000 scanned products and 50,000 scanned lots. Reads use 200-product batches and grouped lot queries rather than one query per medicine. Immutable output pages contain at most 200 records and at most 1 MiB. A server-signed manifest binds their ordered hashes. Pages, manifest, authority revision and required audit commit together with majority write concern; failures expose no partial preparation. Exact/concurrent retries recover the original manifest rather than changing captured evidence.
- Authenticated reads are scoped to the original operator and branch and use `Cache-Control: no-store`: `GET /api/pharmacy/locations/:locationId/offline-authority/:authorityId/snapshot/:page` (`-1` reads the manifest). There are no public ownership/preparation/activation mutation routes. Both ownership and preparation envelopes remain `checkoutEnabled: false`.

## Verification

- Common calculation, source hash/error adapter, existing counter checkout, purchases, returns, tax documents and ownership integration checks passed against disposable synthetic MongoDB fixtures. Recorded groups include 64 calculation/returns cases, 36 checkout/purchase cases and 98 calculation/ownership/tax cases; these groups overlap. The final updated ownership suite passed all **20 cases**, including signed preparation, audit rollback, inconsistent stock/MRP/operator/device, bounded complete pages, restricted-product exclusion, concurrency, immutable storage and scoped read routes. The paging fixture was corrected to reload the actual reviewed product rather than copying its pre-review in-memory state; no review validation was relaxed.
- The frontend pricing/ledger unit run passed **38 cases**. The real Chrome ledger probe passed **17 checks**, including balanced-but-wrong pricing with zero number/stock consumption, mismatched calculation version, exact replay, concurrent tabs, quota rollback, ciphertext corruption and process restart. Its synthetic local commit probe measured about **19 ms**, excluding authorization, preparation, server synchronization and physical printing; it is not an actual-store Save SLA.
- Both package TypeScript checks, changed frontend lint, generated-source parity, isolated API/four-worker bundling, diff checks and the existing patient payment-boundary check passed. See the ignored `.next/pharmacy-pricing-*` and backend `.cache/pharmacy-pricing-*` / `.cache/pharmacy-snapshot-*` evidence. No production/physical-device acceptance claim is made.
- The selected development database's read-only check reports **121 models, 560 expected indexes, transaction capable, ready, no issues**. No real branch was claimed or real invoice/payment/stock written for verification. The sandboxed metadata connection failed; the same read-only check succeeded with network access.

## Required before offline finalization

1. Browser verification of the signed manifest/pages against a trusted signing key, complete durable provisioning and bounded operator unlock across restart. The preparation signature alone grants no checkout authority.
2. Authenticated ordered import of immutable offline invoices, payments and stock, original number/price preservation, lost-response recovery and conflict review.
3. Activation plus counter/offline-shell local Save/Print and compact pending synchronization with bounded retry/backoff. Use the authorized local commit, never an unsigned catalogue estimate.
4. Stop/drain/reconcile for issuing devices; protected backup/key recovery, restore and device/profile replacement. Unused-preparation cancellation is insufficient.
5. Actual weak-network, slow-disk/older-PC and physical printer acceptance, followed by intended-environment release checks. Optional P2 features remain deferred.
