# Pharmacy product, UX and feedback-loop audit — 18 November 2026

## Scope and conclusion

**22 November follow-up:** The stock/archive, customer/payment, mixed-prescription, pickup, credit, reporting and recall workflow changes are documented in [the pilot validation checklist](pharmacy-pilot-validation.md). Earlier findings below are dated observations. Real-store hardware acceptance and actual GST/licence/professional evidence remain unverified; the pending CDCI application does not authorize an import.

Reviewed the existing pharmacy workspace, its 15 capability-controlled sections, pharmacy components and their API/service/model boundaries, public medicine discovery, settings and supplier portal. This builds on the earlier [whole-flow audit](pharmacy-whole-flow-audit.md) and [implementation status](pharmacy-audit-implementation-status-2026-11-15.md); historical findings are not automatically current defects.

The product already has substantial stock, procurement, financial and offline functionality. The useful next increment is to remove friction around those workflows, rather than add another stock, catalogue, checkout or supplier system. This increment fixes confirmed search/navigation problems and reduces unnecessary test setup. It does not certify an actual pharmacy installation or claim that source review proves every interaction works on real hardware.

No new P0 data-integrity defect is asserted by this source audit. A failing relevant regression remains a delivery blocker; these safeguards must not be removed for a faster-looking interaction.

## Architecture and performance decisions

The desired hot path already exists: select cached product → edit quantity locally → send IDs, quantities, confirmed total and payment intent → revalidate actual branch authority, current product/lot/price/tax and customer → allocate invoice number and persist invoice/payment/stock atomically → return committed evidence → prepare next cart and optionally print. Request keys and captured evidence deliberately add protection; removing them to make Save appear instantaneous would create duplicate/incorrect financial records on a bad network.

This increment does **not** claim a newly measured actual-store Save speedup. Existing `PharmacySaveTimings`, browser phase measures and controlled [Save benchmarks](pharmacy-audit-implementation-status-2026-11-15.md) distinguish network, server and print/storage phases. A real configured-store percentile needs actual hardware/network measurements. No speculative backend cache, asynchronous unconfirmed payment or background replay of uncertain writes was added.

Search/filter reads are replaceable and debounced; financial writes are recorded commands with explicit recovery. Pagination stays bounded. The new sales index is declared on the existing Invoice model (`pharmacy_branch_sales_history_v1`); no new collection, dependency or stock migration. Apply/check declared indexes using the existing database index tooling before enabling the change on the selected environment. No live business API mutation, seed or manual index application was issued during this audit; database tests use disposable fixtures.

Contains/literal sales search can still examine many history records for broad terms. The branch index and query time ceiling bound its impact, but a production-volume benchmark is still needed before adding a derived search projection. Do not fetch the full ledger into the browser as a workaround.

## Practical reference checks

The design priorities align with official workflow descriptions for [eVitalRx daily pharmacy operations](https://www.evitalrx.in/products/run-your-pharmacy-efficiently/) and [batch/expiry inventory](https://www.evitalrx.in/solutions/efficient-inventory-management/): efficient counter entry, accurate stock and traceable purchasing matter more than extra dashboards. These are product references, not proof of feature parity or regulatory certification. The implementation uses Ekavyu's own existing services/components.

The test split follows the installed Vitest 5 [project configuration](https://main.vitest.dev/guide/projects) and [performance guidance](https://main.vitest.dev/guide/improving-performance): skip irrelevant setup for reviewed pure tests while retaining persistence isolation where it matters.

Remaining operating/release work, rather than hidden feature completion:

- CDCI/SNOMED affiliate approval is still needed before licensed catalogue ingestion/activation. Provider failures must not prevent use of existing branch products. No assumed freely reusable live medicine feed.
- Actual billing PC, physical thermal/A4 printer, external backup and poor-network/restart acceptance. The user currently has development hardware only. Browser print invocation/PDF checks cannot prove paper output or backup recovery at a store.
- Measure configured-store Save/search p50/p95 and representative large invoice-history search. Existing local benchmarks are not a production SLA.
- Verify issuer, tax, pharmacy licence, pharmacist and controlled supply configuration against the operator's real use. This is not a legal compliance certification; unsupported scopes remain blocked.
- Supplier email/file provider configuration and an actual supplier pilot remain deployment inputs; synthetic portal/document tests do not send messages.
- Broad optional features such as autonomous supplier ordering, unrestricted multi-PC offline final billing, B2B GST workflows and new dashboards are not introduced by this UX audit. Existing explicit limitations remain visible.

This is an incremental product refinement with a documented source review and regression evidence, not a blanket guarantee that all possible defects or hardware cases have been eliminated.
